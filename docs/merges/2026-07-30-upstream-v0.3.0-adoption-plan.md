# lover 吸收 upstream v0.3.0 变更评估与推进方案

## 结论

不再把 upstream v0.3.0 整体 merge 到 `lover`。改为按能力移植：

1. 先移植 Electron 的 Activity/File Diff、Session 信息和 Prompt 导航。
2. 后端只补上述前端能力缺少的最小 payload；其余 v0.3.0 可靠性优化后置。
3. 会话、上下文、Cron、Heartbeat 按 `lover` 的统一会话语义重新评估，不能直接覆盖。
4. Electron 保留本地打包的独立 renderer，只同步协议和选择性移植 WebUI 功能。
5. 浏览器 WebUI 继续由 gateway 提供，与 Electron 共用后端协议，不共用运行时页面。

上次将 Electron 改成远端 WebUI 容器的方案已证明不适合当前部署：NAS WebUI 发布节奏、每台设备的 gateway/token 设置、动态壁纸和桌面能力被绑在一起，且统一会话、Cron 来源、图片与主动消息又需要额外补丁。

## lover 不可破坏的约束

后续每批移植都必须保留：

- `unifiedSession=true` 时，QQ、微信、Electron 等渠道共享 `unified:default`。
- Electron 统一收件箱从权威 Session 恢复历史，并展示消息来源、助手名称与头像。
- Cron/Heartbeat 内部触发消息不污染用户消息列表；主动回复保留任务名称和来源。
- Heartbeat 的 `contextMessages` 仍可配置，不能改成代码固定值。
- AutoCompact、会话裁剪与文件上限不能让当天原文脱离夜间日记任务的可读数据源。
- `nanobot/session/history_store.py` 的原始历史归档继续保留。
- `active_memory`、日记检索、辅助视觉、TTS、桌面上下文、动态壁纸和桌宠相关能力不因 upstream 删除而消失。
- Electron 的 gateway URL、token 和本地偏好按设备保存。
- NAS 部署继续保留源码挂载、代理、Codex OAuth 路径和 Unraid `99:100` 权限策略。

## 后端差异与吸收建议

### 1. Session 持久化

| v0.3.0 | 当前 lover | 决策 |
| --- | --- | --- |
| Session 文件名使用可逆编码，避免 `a:b` 与 `a_b` 冲突 | 使用可读的 `safe_key` 文件名 | 值得吸收，但必须单独做迁移和回滚；不直接 cherry-pick |
| 文件消息上限从 5000 调为 2000 | 上限 5000，并把被裁剪原文写入月度 archive | 保留 lover archive；上限是否调整由日记验证决定 |
| Session 内存缓存最多 128 个 | 缓存无界 | 优先吸收 |
| 列表、损坏文件修复、旧路径迁移更健壮 | 已有原子写和修复，但覆盖较少 | 分项吸收 |
| 删除 Session 时同步清理旧路径 | 只删除当前路径 | 可低风险吸收 |

相关 upstream 提交：

- `463f5367`、`cf2f5896`、`00a907c4`：存储键碰撞修复。
- `3ce77633`、`c90e4330`、`89dc34df`：编码恢复与损坏文件修复。
- `d35f99ab`：限制内存 Session 缓存。
- `7cf3c71e`：在持久化边界执行文件上限。
- `33638417`：删除 Session 时清理旧路径。

建议拆成两批：

1. 先做缓存上限、读取容错和删除清理，不改变文件名。
2. 再做可逆存储键迁移。迁移前后都用 Session metadata 中的真实 `key` 作为身份，UI 不依赖文件名。

### 2. Context、AutoCompact 与 Dream

v0.3.0 的主要变化：

- 默认上下文窗口从 65,536 调到 200,000。
- 移除固定 `maxMessages` 配置，按模型上下文窗口动态估算 replay 消息数。
- Recent History 从字符上限改为 token 上限。
- Idle AutoCompact 默认启用，保留最近合法用户轮次，默认目标后缀约 8 条消息。
- Idle Compact 改为总结完整未压缩尾部。
- Dream cursor、空变更 commit、行尾差异和损坏历史处理更稳。

当前 `lover` 额外依赖：

- `maxMessages` 控制历史重放。
- `contextMessages` 控制 Cron/Heartbeat 注入统一会话的条数。
- Session 裁剪原文进入 archive，夜间日记读取当天完整消息。
- Active Memory 和日记检索依赖现有历史边界。

吸收策略：

- 吸收 token 预算算法、Dream cursor 单调性、损坏历史忽略、空变更不提交等修复。
- 保留 `maxMessages` 作为用户上限；实际 replay 取“配置上限”和“token 预算”较小值。
- 保留 `contextMessages`，它是主动任务上下文，不等同于普通对话 replay。
- 暂不采用“默认开启 Idle AutoCompact”。
- AutoCompact 要先证明被摘要替换的原文已落入 archive，且夜间日记只读 archive/原始事件，不读压缩后的 Session 表象。

相关 upstream 提交：

- `40282e3b`：按上下文窗口缩放 replay。
- `973a5ee5`：Recent History 使用 token 上限。
- `0863e6e5`：Idle Compact 总结完整 Session 尾部。
- `09962895`、`3ce0cd97`：保留合法用户轮次。
- `be058c09`、`a81c5e70`：Dream cursor 防回退与非法值。
- `c111aaa7`、`f0c989ba`：Dream commit 与审计修复。

### 3. Cron、Automation 与本地 Trigger

v0.3.0 将 Cron 从“向渠道发送一条触发消息”改为“绑定创建它的 Session，作为正常 Agent turn 执行”：

- Job 保存 `session_key` 和原始渠道投递上下文。
- 内部触发 prompt 标记为隐藏历史。
- 结果回到原 Session，并记录 run history。
- WebUI 可查看、编辑、立即运行和删除 Automation。
- 新增 session-bound local trigger，带恢复和审计。

这个方向值得吸收，但不能照搬。上次合并暴露了三类缺口：

1. Electron 统一收件箱创建的任务可能被错误绑定到 `websocket:inbox:unified`，而不是 `unified:default`。
2. 隐藏触发消息未在历史转换层过滤，会污染消息列表。
3. Cron 来源只存在于实时 WebSocket metadata，重启后任务名称丢失。

推进要求：

- `unifiedSession=true` 时，Electron 创建的 Job 固定绑定 `unified:default`。
- Job 的 `origin_channel` 只决定实际投递渠道，不决定 Agent Session。
- 隐藏触发标记在实时流和 Session 历史转换两条路径都生效。
- `{kind: "cron", label: job.name}` 随 assistant turn 持久化，刷新后仍能展示来源。
- Heartbeat 使用同一执行框架，但不伪装成普通 Cron 消息。
- 第一阶段不引入 local trigger，先把 Cron/Heartbeat 语义稳定。

可先独立吸收 jobs.json 读取容错：

- `afed32b0`：camelCase/snake_case 双格式。
- `b81c0558`、`b6156fdd`、`0b1b02f1`、`299bcf49`：字符串、null 与损坏 run history 容错。

Session-bound Cron 应以 upstream `a326ba40` 到 `b24b5f19` 的行为为参考重新移植，不直接 cherry-pick 整段提交。

### 4. Heartbeat

v0.3.0 的 Heartbeat 仍由受保护 Cron Job 驱动，新增或修复：

- HEARTBEAT 文档明确“无有用结果时保持安静”。
- evaluator prompt 可自定义。
- 空执行保留历史，不错误推进。
- 选择最近活跃目标时排除 archived Session。
- prompt 从“汇报任务”改为“实际执行任务”。

建议吸收这些行为，但保留 lover 的：

- `contextMessages` 最近消息注入。
- 统一会话作为默认上下文与 Electron 可见目标。
- `desktop_context`、TTS、辅助视觉等工具说明。

Heartbeat 配置最终应明确分成：

```text
执行定义：HEARTBEAT.md
上下文数量：config.gateway.heartbeat.contextMessages
执行频率/模型/evaluator：config
投递目标：统一会话规则 + origin delivery
```

### 5. Provider 与模型运行时

v0.3.0 的高价值变化：

- 不可变的 model runtime resolver，避免运行时修改全局 provider。
- Model preset 可按 Session 选择。
- 跨 provider failure domain 回退。
- Codex fast mode、Codex proxy 一致性、请求阶段错误标记。
- OpenAI/Anthropic tool-call ID、异常 content block、UTF-16 surrogate 等兼容修复。
- provider-scoped proxy、动态 custom provider、Kimi Coding/K3、OpenCode 等。
- 配置文件运行时监听，图片生成设置可热更新。

建议分层吸收：

| 层级 | 内容 | 决策 |
| --- | --- | --- |
| P0 | Codex proxy、图片 SSE、请求错误分类、tool-call 数据修复 | 优先 |
| P1 | provider-scoped proxy、配置热加载 | 吸收，保留环境变量代理 |
| P1 | immutable runtime resolver、跨 provider fallback | 作为一个完整批次 |
| P2 | Session 级 model preset | 不吸收；当前只使用统一会话 |
| P2 | 新 provider | 按实际使用需求加入 |

必须保留 lover 的 preset 级 `vision_model` / `vision_provider`，不能因为 v0.3.0 schema 删除而退化为只能配置独立视觉模型。

### 6. Gateway、WebSocket 与 HTTP API

v0.3.0 将 gateway、WebSocket channel 和 HTTP 路由进一步拆分：

- `nanobot/gateway/` 负责进程与服务生命周期。
- `nanobot/channels/websocket/runtime.py` 负责 WebSocket channel。
- `nanobot/webui/` 承担 Session、Settings、Automation、媒体和 bootstrap API。
- bootstrap token、远程访问、文件预览和关闭顺序更安全。
- restart 完成提示在渠道重连后发送。

当前 `lover` 已有 `ForkGatewayHTTPHandler`、统一收件箱 fan-out、presence、截图、媒体签名和自定义设置 API。不能用 v0.3.0 的 manager/runtime 整体覆盖。

建议：

1. 先写协议契约测试，固定 Electron 使用的 HTTP 路由和 WebSocket frame。
2. 移植生命周期和安全修复，例如 `88c38e9b` 的 restart 完成投递、`d4e02947` 的关闭顺序。
3. 需要某个 v0.3.0 UI 功能时，再补对应 API；不为“接口齐全”一次搬完所有 Settings 路由。
4. Electron 和浏览器 WebUI 共用协议，但分别构建与发布。

### 7. Channel 包结构

v0.3.0 将内置 Channel 从单文件迁移为自包含包，包含：

- `runtime.py`
- `manifest.py`
- validation/connect
- Channel 自有测试
- WebUI 设置插件与多语言资源

这是 319 个 `nanobot/channels` 路径变化的主要来源。架构更利于可选依赖和 WebUI 自动发现，但对 lover 的 QQ、微信、统一会话与来源映射冲击很大。

决策：暂缓整体迁移。先移植实际需要的 QQ/微信连接稳定性修复；等后端 Session/Cron/协议稳定后，再开独立分支做 Channel package migration。

### 8. Docker

v0.3.0 默认偏向通用部署与 Render：

- 镜像内 `nanobot` 用户为 `1000:1000`。
- entrypoint 从 root 降权。
- WebUI 默认使用镜像内构建产物。
- 加入 Render 配置和更严格的默认安全能力。

lover 面向个人 Unraid/NAS：

- 源码与配置目录直接挂载。
- 需要容器内代码热更新。
- 需要 `99:100` 对齐 Unraid。
- 需要 NAS 代理与 Codex OAuth 持久化。

决策：不吸收默认用户和挂载策略；只选择性吸收 entrypoint 失败保护、健康检查与关闭安全修复。

## Electron 与 v0.3.0 WebUI 对比

### 代码分化程度

把 `electron/src/renderer/` 映射到 `webui/src/` 后：

- 50 个文件存在同名对应。
- 只有 8 个 blob 完全一致。
- 42 个已经产生实质差异。

分化最大的区域：

- `SettingsView`
- `App`
- `ThreadComposer`
- `AgentActivityCluster`
- `MessageBubble`
- `useNanobotStream`
- `types.ts`
- `api.ts`

这些文件不能整文件从 WebUI 覆盖到 Electron。

### 能力矩阵

| 能力 | Electron 当前 | v0.3.0 WebUI | 推进决策 |
| --- | --- | --- | --- |
| Renderer 发布 | 本地随 Electron 打包 | gateway 提供静态资源 | 必须分开 |
| Gateway URL/token | 每台设备本地保存 | 默认同源 bootstrap | 保留 Electron |
| 统一收件箱 | 跨 QQ/微信/Electron，展示来源 | 以普通 Topic/Session 为核心 | 保留 Electron |
| 动态壁纸/透明窗口 | 完整支持 | 不适用 | 保留 Electron |
| 托盘、快捷键、桌面截图 | Electron 原生 | 仅提供 host bridge 抽象 | 保留 Electron main/preload |
| TTS 与自动播放 | Electron 有独立队列与设置 | 主要是语音输入/附件 | 保留 Electron，不吸收 voice recorder |
| 助手头像/名称/来源 | Electron 有定制展示 | 官方展示较弱 | 保留 Electron |
| Topic 列表 | 统一 Inbox + 渠道视图 | Topic、置顶、重命名、删除 | 只吸收置顶/搜索等需要项 |
| 新建 Topic | Electron 可屏蔽 | 官方主流程 | 继续屏蔽 |
| 回复分叉 | Electron 预期屏蔽 | 官方支持 fork-from-here | 不吸收 |
| 模型切换 | Electron 有设置和底部信息 | Composer 内切换、Session 级 preset | 不吸收；只使用统一会话，无需 Session 级切换 |
| Session 信息 | 有上下文占比定制 | Session popover、token heatmap | 优先移植 popover 数据展示 |
| Prompt 导航 | 无独立 rail | 长对话 PromptRail/Navigator | 可独立移植 |
| Agent activity | 单个大型定制组件 | 拆分 reasoning/web/file/MCP/generic tool 行 | 移植数据模型和子组件，不覆盖容器 |
| 文件 diff/语法高亮 | Electron 有基础展示 | 官方更完整 | 优先移植 |
| 图片附件 | 已支持剪贴板、拖放和预览 | 支持图片与文档 ingress | 保持现状 |
| 语音输入 | TTS 为主 | `useVoiceRecorder` + shared transcription | 不吸收 |
| Automation 管理 | 主要依赖任务消息 | 官方有查看、编辑、立即运行、删除 | 当前不吸收 |
| Skills/Channel 设置 | Electron 有自定义 Apps/设置分区 | Skills catalog + Channel plugin UI | 按需移植，不能覆盖设置页 |
| 首次引导 | Electron 有 gateway 连接流程 | 官方 provider/channel setup | 保留 gateway 流程；provider 引导后置 |
| 移动端响应式 | 桌面窗口 | 官方重点优化 | 不作为 Electron 优先项 |

### 当前确认的前端范围

本轮只推进三项：

1. Activity 展示与文件 Diff。
2. Session 信息、token 和上下文占用。
3. Prompt 导航。

不做模型切换、文档附件、语音输入和 Automation 管理页。除非三项功能缺少必要数据，否则不改后端。

## 当前推进批次

每批从当前 `lover` 新开分支，独立提交、验证、合回。不要建立一个持续数周的大型升级分支。

### Batch 1：Electron Activity 与 File Diff

## 每批验收矩阵

后端批次至少验证：

- QQ、微信、Electron 发出的消息都进入 `unified:default`。

- 动态壁纸首次打开即加载。
- 设置页切换不销毁消息列表。
- 长 reasoning 折叠后底部消息不被遮挡。
- 音频样式、自动播放、图片和文档附件符合 Electron 交互。
- 新建 Topic 与 fork 按钮仍隐藏。
