## 1. 总体方向

从指定上游版本在当前项目建立并切换新分支，以最新 WebUI 作为 Electron 渲染层基础，按需要补回个人功能。不要逐个重放 lover 的历史提交，不再维护一套完整复制后长期分叉的聊天 UI。

产品仍是伴侣 AI：保留统一收件箱、跨渠道的连续对话，不以多话题、多会话工作台为主要交互。对话运行、子代理、cron、心跳先使用最新上游，体验后再决定需要调整的部分。空闲压缩关闭；用户进一步倾向沿用 lover 的压力触发、部分压缩与原文移出活跃文件的行为，具体与上游集成边界见 5.5。

原始对话不能因自动压缩或存储裁剪而彻底销毁，必须有可追溯、可读取的持久化记录。摘要、Dream 记忆、主题卡均不能代替原文保存。

准备进展：本地 main 已快进到上游 `4420ad58`，已从 `v0.3.5` 建立 `lover-next` 分支，并在当前项目目录切换到该分支；额外 worktree 已移除。已新增 Electron 基础壳并完成第一轮 review 修复；尚未迁移运行数据或删除旧功能。F15、F16、F19 的“不迁移”已记录；不在本轮清理旧 lover 或未跟踪的规格文件。

## 3. Electron 复用最新 WebUI：可行，但需要宿主适配

上游 `webui/src/lib/runtime.ts` 已定义 `RuntimeHost` 与 `window.nanobotHost`，支持原生运行环境、目录选择、重启引擎、日志/诊断和 WebSocket bridge。这提供了复用基础；不是把网页塞进窗口后所有旧桌面功能就自然存在。

建议路线：

1. Electron 继续负责窗口、托盘、快捷键、通知、截图、系统媒体控制和本地视频资源等桌面能力。
2. 以同一份上游 WebUI 源码/构建为主要 renderer，复用聊天、Markdown、工具、模型/设置页面和网络协议。
3. 通过现有原生宿主接口连接 Electron；上游没有的必要能力再增加小范围桥接。
4. 在桌面入口适配统一收件箱，减少不需要的多话题/分屏操作；它不是只隐藏侧栏，还要核对历史读取、发送目标和跨渠道事件。
5. 最后补外观、笔记库、MiniMax 播放和本地伴侣视频，不预先复刻旧 UI。

优先让共用组件保持接近上游，桌面特有布局和能力留在 Electron 宿主适配中。若确需修改根 `webui/`，应限定为本次明确要求的 UI 复用和必要接入，不顺带改造浏览器产品其他流程。

需要在实施中核对：远程 NAS gateway 的地址与鉴权、桌面宿主本地文件路径、附件 staging、CSP/原生桥接、重新连接与音频重播。当前仅确认接口基础，没有做 Electron 集成验证。

### 已确认：统一收件箱接口与身份方案

- Electron 使用一个稳定的 `chat_id` 作为发送、订阅、停止与恢复的通信身份，不因每次启动生成新聊天。
- 后端模型会话使用 `unified:default`；它与前端 `chat_id` 不等价。不能把同名 ID 直接交给 WebUI 就假设会自然映射正确。
- 优先扩展现有会话解析，复用 `/api/sessions/{key}/webui-thread` 的响应格式、分页和历史构建，不复制一套 inbox 历史实现。
- 如确需 inbox 专用入口，只增加薄的转接层。跨渠道实时转发、上下文统计与任务控制都要与统一会话映射一致。

## 4. F07：可以省去专用工具，不能删掉 Active Memory 的搜索依赖

用户已知道并会向 AI 提供日记库位置，可以先让模型使用普通文件/搜索工具做主动查阅，不再专门迁移一个日记搜索工具入口。

但 Active Memory 不是日记库的完整替代品：自动召回只挑选相关片段，可能漏掉明确查询所需的细节。当前 `active_memory.py` 还直接从 `diary_search.py` 导入：

- `canonical_diary_files`：冲突副本与重复来源处理；
- `contains_diary_term`、`diary_body`、`diary_excerpt`：命中、正文与片段提取；
- `search_diary_files`：原始日记搜索。

建议迁移时保留这些真正用到的函数作为 Active Memory 内部实现，不再注册 `DiarySearchTool`。不要为了移除模型工具而删除整个文件，也不需要提前造新的检索框架。

验收：自动召回能接上用户经历；用户明确要求查某日日记、某件往事或原文时，普通工具能访问到正式来源。日记库路径和读取权限应进入实际运行配置/工作区说明，仅“知道路径”并不代表沙箱允许访问。

该方案是针对用户疑问的建议，尚未实施。

## 5. 记忆与历史：本地、上游实际如何保存

### 5.1 当前 lover：确实已按月归档 JSONL

当前 `nanobot/session/history_store.py`：

- 写入 `<sessions_dir>/archive/YYYY-MM.jsonl`；当前 SessionManager 的 sessions_dir 是 `<workspace>/sessions`。
- 月份取每条消息自身的 `timestamp[:7]`，没有时间戳时写 `unknown.jsonl`。
- 每行序列化原消息 dict，不是仅保存 LLM 摘要；归档搜索在 `session_search.py` 中使用 grep，不依赖 SQLite。
- `session_key` 和 `reason` 虽然传入写入方法，但目前没有额外包进归档行；不能据此假设归档天然带有完整会话归属信息。

当前自动/手动上下文整合与空闲压缩路径会把裁掉的原始消息送入该归档。除此以外，`memory/history.jsonl` 保存整合摘要/降级材料，供 Dream 使用，是另一种文件，不能混为原始对话归档。

**已发现的保真缺口（只记录，不在本轮修复）：**

- 归档追加失败被捕获并只记 warning，调用方仍可能保存裁剪后的会话；因此不能承诺“当前任何裁剪都不会丢原文”。
- 文件消息数上限路径调用 `enforce_file_cap(on_archive=memory.raw_archive)`，没有走同一个月度原文归档入口；其降级材料也不能等同完整原文备份。

这些是新方案需要避免的问题，不意味着本轮已确认线上发生过数据丢失。

### 5.2 最新上游：正常压缩只改变模型可见窗口，原文仍在会话文件

已核对 `4420ad5` 的 `Session.commit_summary_checkpoint()`、`get_history()`、`Consolidator.compact_idle_session()`、Runner 保存和 JSONL 保存路径：

- 提交累计摘要、更新 `last_archived` 边界，并插入内部继续标记。
- 后续模型请求使用摘要和边界之后的内容，不再重放全部旧消息。
- 原始 `session.messages` 仍保留；保存时逐条写入会话 JSONL。
- 默认会话位置是配置目录的 `sessions/<workspace-id>/`，也支持显式存储根目录。
- 没有发现旧版 `FILE_MAX_MESSAGES` / `enforce_file_cap` 自动裁剪路径。该结论限于核对的提交，不能推广为所有未来版本都永久保留。

所以正常压缩后的“归档位置”仍是原会话 JSONL，而不是另存的月度 archive。**逻辑上不再送进模型，不等于物理删除。**

### 5.3 上游何时触发

| 触发 | 条件/默认值 | 原始对话去向 |
| --- | --- | --- |
| 运行中上下文压力 | 请求估算/对应 provider 用量达到有效输入预算；依模型上下文窗口与预留计算，不是固定消息条数 | 累计摘要检查点替代模型重放，原始会话消息保留 |
| Provider 原生压缩 | 支持该能力的 provider 在其压缩条件满足时执行，上游同步本地摘要检查点 | 本地已持久化会话原文保留；私有 provider state 与公开原文不是一回事 |
| 空闲自动压缩 | 默认空闲 15 分钟；扫描默认最小间隔 60 秒，跳过有运行任务的会话，需要有未归档消息；TTL 为 0 可禁用 | 更新摘要和边界，保留原始会话消息；不是精确到 15 分钟必然执行 |
| 手动 `/compact` | 用户触发，调用同一摘要检查点路径 | 保留原始会话消息 |
| Dream | 默认启用、每 2 小时，通过系统 cron 调度；支持配置调整 | 消费 `memory/history.jsonl` 的未处理材料，更新长期记忆；不等于裁剪原始会话 |

Dream 输入日志另有清理：`compact_history()` 默认上限 1000 条，超过时可移除较旧的已处理记录，同时保护未处理记录。这是记忆加工日志的保留策略，不是会话原文归档策略。若希望连每一版中间摘要也永久保存，需要另行确认；当前明确要求是对话原文不能因裁剪销毁。

### 5.4 “原文不能销毁”还需要覆盖重置/删除路径

最新上游 `/new` 先 `session.clear()` 并保存，再对尚未归档的快照异步生成记忆摘要。它没有先创建完整原文副本。删除会话接口也会删除会话文件。

因此，不能把“普通压缩保留原文”扩大成“任何操作都不会丢原文”。建议新版本遵守下面的最低契约：

1. 自动压缩优先直接沿用上游，不为每次压缩重复存一套月度副本，不引入数据库。
2. 任何会物理移除原始记录的重置、清理或迁移，先完成可验证的原文归档；归档失败则保留原文，不继续破坏性步骤。
3. 删除的含义要明确：普通清理先进入可恢复归档；只有用户明确要求彻底删除时才另行处理。具体交互留到实施方案确认。
4. 旧 lover 的 `sessions/archive/*.jsonl` 原样保护，保持可搜索；不能只迁移活跃会话就遗漏过去裁掉的消息。
5. 摘要、Dream 文件和主题卡均不作为原始会话的替代备份。附件路径与资源也需要可用，JSONL 中有引用不代表附件实体已归档。

待讨论：未来原文是否必须另存按月 JSONL？当前需求用“上游会话文件保留原文 + 物理移除前归档”即可满足主要目标；若必须统一按月查阅，再决定组织形式，不先维护重复存储系统。

### 5.5 第二轮倾向：压力触发、部分压缩、原文归档后移出

用户提出保留 lover 的使用效果：尽量保留近期原始对话，达到上下文容量压力后再压缩，并把已压缩原文移出活跃会话文件。该方向区别于完全沿用上游的全历史摘要检查点；不等于整体搬回旧 Consolidator。

明确采用配置关闭空闲压缩：`agents.defaults.idleCompactAfterMinutes = 0`。上游兼容旧名 `sessionTtlMinutes`，建议新配置只写规范名。不要把 `idleCompactCheckIntervalSeconds` 设为 0 当作关闭，它控制扫描频率。当前 lover 的空闲阈值默认已为 0，上游默认是 15。

核对后的 lover 实际行为：

- token 压力达到有效输入预算时，分批压缩旧前缀，目标默认是预算的 50%（`consolidationRatio = 0.5`），保留近期原始后缀；受合法消息边界、压缩轮数与失败条件约束，不保证精确落在 50%。
- **并非只有 token 满才压缩**：回放消息窗口超过 `maxMessages` 也会先归档，当前 schema 默认 120。手动强制压缩、文件上限也是其他边界。迁移不能把这些旧条件不加选择地搬回。
- 物理裁剪减少活跃文件大小，但不会在“已从模型重放排除”的基础上再次减少模型 token；这是存储组织决定，与触发时机是两件事。

建议待实施方案落实为：到有效输入预算才自动触发（预留输出和安全空间，不等服务端报溢出）；优先压缩旧前缀、保留近期原文；可靠归档后再物理裁剪。50% 可作为沿用 lover 的初始候选，不因本次讨论新增复杂配置。

移植时保留上游累计摘要、工具调用边界和错误恢复；裁剪后必须同步摘要边界与 provider continuation state。归档失败不能继续裁剪，历史查询/分页需能读到移出的原文。支持 Responses 原生压缩的路径可能按约 90% 窗口提前触发，关闭空闲压缩不会关闭它，需要在集成方案中统一说明，不能承诺仅靠一个配置实现所有“满才压缩”的行为。

## 6. 桌面感知、语音、伴侣与技能

## 10. 统一收件箱第 1 步：固定身份与模型状态映射

本步已实现，未包含统一历史聚合、跨渠道实时转发或侧栏精简。前提是后端已开启 `agents.defaults.unifiedSession`；不在实现中改写用户配置。传给状态投影的 lambda 仅延迟读取这个配置值：开启时查询 `unified:default`，关闭时仍查询 `websocket:desktop`。Agent 的统一执行已有上游支持，新增的是 WebUI 查询目标对齐。

### 三个名字分别负责什么

| 标识 | 职责 | 本步行为 |
| --- | --- | --- |
| `desktop` | WebSocket 的 `chat_id`，决定向哪个桌面订阅发送事件 | Electron 固定使用，断线重连仍订阅此 ID |
| `websocket:desktop` | WebUI 的公开会话 key，用于页面路由和展示记录 | 保持上游格式；未发送消息前由客户端提供固定入口，不为此写空会话文件 |
| `unified:default` | Agent 实际运行的 session key，拥有模型历史、任务与摘要状态 | 发送和 `/stop` 使用上游既有统一路由；新增查询映射读取同一状态 |

发送链路：Electron preload 的 `fixedChatId` → WebUI RuntimeHost → NanobotClient → WebSocket 入站 → AgentLoop 现有统一路由。核心循环没有为伴侣模式增加另一套处理分支。

查询链路：`GET /api/sessions/websocket%3Adesktop/context` → WebUI 的 `model_session_key()` → 统一 Session 快照。重连的 attach/hydration 同样读取统一会话的模型预设、用量、goal 与恢复元数据；返回的实时事件仍标记 `chat_id=desktop`，让桌面能正确接收。

只将保留的 `websocket:desktop` 入口做此查询映射，普通浏览器的话题 ID 和查询语义不变。历史接口暂未改成统一历史；模型能续上对话与界面能展示全部旧历史是两项独立工作。

新建动作在固定模式复用已有入口，不发送 `new_chat`，也不等同 `/new` 或清空模型历史。侧栏暂时保留上游布局；点击其他话题进入聊天时会回到固定入口，临时/分叉创建被拒绝，后续再收敛这些 UI 入口。

验证：前端相关测试 200 项通过；后端身份、状态投影与统一执行测试 29 项通过，上下文 HTTP 路由两种配置分支已通过；Ruff、选定前端文件 ESLint、TypeScript/Vite 构建和正式打包通过。打包版模拟 gateway 冒烟确认发送及刷新均使用 `desktop`，不发 `new_chat`。未自动重启用户正在运行的 gateway 或 Electron，也未对真实模型发起测试请求。

## 13. 跨渠道完整消息自动同步

范围明确为完整消息自动同步，不额外开启各渠道的逐字流式输出，也不更改它们的原有投递。用户输入在其开始执行并已落盘后显示；排队期间不伪造未持久化历史。
